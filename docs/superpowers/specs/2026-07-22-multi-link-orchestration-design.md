# Оркестрация нескольких BLE-линий (подпроект A групп BMS)

Дата: 2026-07-22
Статус: дизайн утверждён

## Задача

volty уже умеет транспорт из нескольких **пакетов** (мультипакетный фундамент,
Begode). Но все пакеты сейчас приходят по **одной** BLE-линии: репозиторий
держит один `currentSession`, один `reconnectJob`, одну `ConnectionTarget`, а
`connect(vehicle)` читает единственный `vehicle.bmsAddress`.

Группа независимых BMS (2×ANT, ANT+JBD и т.п.) — это несколько пакетов за
**разными** BLE-адресами, то есть несколько одновременных сессий. Этот
подпроект учит репозиторий держать N линий на один транспорт. Пользовательского
эффекта нет: транспорт с несколькими адресами создать пока нечем (это
подпроект B). A — поведенчески нейтральный фундамент, как первые пять шагов
мультипакета.

## Что уже готово и не меняется

- `VehicleConnection` — оркестратор N пакетов: `submit`, `markOffline`,
  живость, `snapshot`. Однопоточен по построению.
- `PackAggregator` — свёртка пакетов в агрегат.
- Живость пакета (staleness sweep, `PackSampleGate`) и `isPartial`.
- `ConnectionSession` — жизненный цикл **одной** сессии: коннект, подписка,
  watchdog, teardown; отдаёт сэмплы через `onSample`.

Всё это про N пакетов и уже работает. A кормит их от N линий вместо одной.

## Отображение пакетов на линии — сердце подпроекта

У транспорта есть `packs: List<Pack>`, у каждого пакета — `index` и
`bmsAddress`. Линии группируются по **различному адресу**:

| Транспорт | Пакеты | Линии |
|---|---|---|
| Begode | `Pack(0, addrA)`, `Pack(1, addrA)` | одна линия addrA, `packCount=2`, владеет `[0,1]` |
| Группа 2×ANT | `Pack(0, addrA)`, `Pack(1, addrB)` | линия addrA → `[0]`, линия addrB → `[1]` |
| Begode + доп | `Pack(0,addrA)`, `Pack(1,addrA)`, `Pack(2,addrB)` | addrA → `[0,1]`, addrB → `[2]` |

**Правило.** Для каждого различного адреса собираем его пакеты, отсортированные
по `index`; это глобальные индексы, которыми владеет линия, в локальном порядке.
Сессия отдаёт сэмпл с **локальным** индексом (0-based внутри своего протокола);
линия переводит его в глобальный: `globalIndex(local) = ownedIndices[local]`.
Репозиторий сабмитит в `VehicleConnection` уже глобальный индекс, потому что
оркестратор ключуется глобальными.

`connectionPacks`/`expandedTo` (число пакетов от `packCount` протокола)
применяется **на линию**, а не на транспорт: линия расширяет свои сохранённые
пакеты до `packCount` своего протокола. Для группы 1×ANT это 1, для Begode-линии
это 2.

## Барьер сериализации

Сегодня сессия зовёт `onSample`, который синхронно вызывает
`vehicleConnection.submit`. При одной линии это безопасно: единственная
корутина `observeJob`. При двух линиях — две корутины на разных потоках пула
одновременно мутируют незащищённый список `VehicleConnection.states`. Настоящая
гонка. Этот барьер был обещан в исходной спеке мультипакета и не построен,
потому что до сих пор был недостижим.

**Решение — канал, не мьютекс.** `VehicleConnection` спроектирован
«однопоточно по построению, а не по блокировке»; мьютекс нарушил бы этот
инвариант, канал — сохраняет.

- `Channel<PackSample>` (unlimited или разумно ограниченный буфер), где
  `PackSample(globalPackIndex, BmsData, sections)`.
- Каждая линия в своём `onSample` **только пишет** в канал — с уже переведённым
  глобальным индексом.
- Единственная корутина-потребитель на транспорт сливает канал и вызывает
  `vehicleConnection.submit(...)`, потом делает то, что сейчас делает `onSample`
  после submit: пуш агрегата в ring buffer **перед** `_activeData` (порядок
  для графика), апдейт `_activeVehicleData`.
- Порядок «буфер перед activeData» и его комментарий переезжают в потребителя.

При одной линии у канала один писатель и семантика прежняя.

## Веер линий

`currentSession: ConnectionSession?` → структура, держащая **список линий**.
Каждая линия (`PackLink`, internal):

- свой `ConnectionSession`;
- свой цикл переподключения (сегодняшний `reconnectJob`/`startReconnectLoop`,
  но на линию);
- своя `ConnectionTarget(address, type, ownedIndices)`;
- флаг живости (онлайн, если её watchdog не сработал).

`doConnect(vehicle)` больше не берёт один адрес. Он:

1. вычисляет линии из `vehicle.packs` (группировка по адресу);
2. создаёт один `VehicleConnection` на все пакеты транспорта;
3. поднимает канал и корутину-потребитель;
4. поднимает каждую линию, **со сдвигом старта** `BleConfig.linkStaggerMs`
   (одновременный GATT на Android капризен), каждая пишет в общий канал;
5. транспорт считается подключённым, как только **первая** линия дала сэмпл.

Отключение (`disconnect`) рвёт все линии, отменяет все циклы, закрывает канал,
чистит оркестратор — под тем же `sessionLock`, что и сейчас; замок
нереентерабельный, писать под ним аккуратно.

## Состояние транспорта — свёртка линий

`ConnectionState` транспорта = свёртка по линиям:

| Условие | Состояние |
|---|---|
| ни одна линия ещё не дала первый сэмпл | `Connecting` |
| хоть одна линия онлайн | `Connected` |
| все оффлайн, хоть одна пробует переподключиться | `Reconnecting` |
| все сдались | `Failed` |

Отдельного `Degraded` нет — частичность уже выражена `isPartial` и живостью
пакетов. Линия падает → её пакеты через staleness sweep уходят оффлайн →
`isPartial=true`, транспорт остаётся `Connected`, её цикл переподключения ищет
её сам. Появилась в радиусе — подхватилась.

## Неполное первичное подключение

Сохранённая группа, в радиусе только часть линий: поднять все, транспорт
становится `Connected` по первой ответившей, недостающие линии помечены оффлайн
(их пакеты никогда не материализовались или ушли в staleness) и дожимаются
циклом переподключения в фоне. Никакого «ждать все» — живая линия работает
сразу.

## Что не входит (подпроект B)

- UI «добавить вторую BMS» и выбор топологии.
- Починка `scanAll`'s `associateBy { it.bmsAddress }` (узнаёт только первый
  пакет) и `VehicleEditComponent` (схлопывает в один пакет через
  `singlePackVehicle`).
- Персистентность многолинийного транспорта как группы.
- Любой способ **создать** транспорт с несколькими адресами.

До подпроекта B ни один сохранённый транспорт не имеет пакетов с разными
адресами, поэтому A ничего не меняет для пользователя — это его тест на
нейтральность.

## Тесты

Всё на фейках, без реального BLE, как в существующих тестах репозитория.

- **Отображение пакетов на линии:** группировка по адресу даёт правильные
  наборы владения для Begode (одна линия, `[0,1]`), группы (две линии, `[0]` и
  `[1]`), смешанного случая; локальный→глобальный перевод корректен.
- **Барьер:** два фейковых источника пишут в канал вперемешку из разных
  корутин; потребитель сливает; `VehicleConnection` видит оба пакета, состояние
  консистентно (гоняется под `runTest` с реальной конкуренцией, насколько
  тестовый диспетчер её даёт).
- **Свёртка состояний:** первая линия онлайн → `Connected`; одна из двух падает
  → `Connected` + `isPartial`; обе падают → `Reconnecting`; все сдались →
  `Failed`.
- **Независимый реконнект:** падение линии A не трогает цикл линии B; A
  переподключается сама.
- **Неполное подключение:** две линии заявлены, отвечает одна → `Connected`,
  вторая оффлайн и в цикле.
- **Нейтральность:** однолинийный транспорт (в т.ч. Begode) поднимает ровно
  одну линию, один писатель канала, поведение и порядок сэмплов неотличимы от
  нынешних; `KableBmsRepositoryDisconnectRaceTest` и
  `KableBmsRepositoryOnAppResumedTest` проходят без правок — это сигнал, что
  жизненный цикл не задет.

Числа с узкими допусками, тесты видят красный до реализации.

## Риски

| Риск | Смягчение |
|---|---|
| Развязка `doConnect` задевает выстраданную гонку disconnect-vs-reconnect | Два гоночных теста проходят без правок — обязательное условие |
| Канал добавляет задержку между сэмплом и отрисовкой | Буфер канала небольшой; при 1–6 Гц незаметно; порядок буфер-перед-activeData сохранён |
| Одновременный GATT на нескольких линиях | Старт со сдвигом `linkStaggerMs`; Android держит ~7 линий, нам нужно 2–3 |
| `sessionLock` нереентерабельный | Писать `vehicleConnection`/линии под ним, не брать дважды — как уже сделано |
