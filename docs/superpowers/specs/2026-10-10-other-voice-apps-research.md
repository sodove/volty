# Other mature Android group voice apps: source review

Checked on 2026-10-10 against pinned source revisions listed below. This is a source-path review, not an independent device benchmark. Telegram is outside scope. The earlier general survey already covers LiveKit, Twilio and Jitsi as choices; this report focuses on concrete Android audio ownership and reuse boundaries.

## Findings

### Element: distinguish the shipped Element X call path from its new native component

At Element X commit [f12b9c77](https://github.com/element-hq/element-x-android/commit/f12b9c77d539010a257a4bbdca84dfbf38530008), CallScreenView constructs an Android WebView through CallWebView and wires WebViewAudioManager; the manager changes Android communication mode and bridges device selection to the Element Call web app. This is the production call path visible in Element X, so it is not evidence of an Android-native LiveKit track renderer. See [CallScreenView.kt](https://github.com/element-hq/element-x-android/blob/f12b9c77d539010a257a4bbdca84dfbf38530008/features/call/impl/src/main/kotlin/io/element/android/features/call/impl/ui/CallScreenView.kt#L101-L129) and [WebViewAudioManager.kt](https://github.com/element-hq/element-x-android/blob/f12b9c77d539010a257a4bbdca84dfbf38530008/features/call/impl/src/main/kotlin/io/element/android/features/call/impl/utils/WebViewAudioManager.kt#L170-L188).

Element’s separate element-call-android native component, commit [07083066](https://github.com/element-hq/element-call-android/commit/070830669d79bf76835f16321d3a4c1b102a2e98), has a very different boundary:

- RustMatrixRtcMediaSession.playAudioOf() opens a remote microphone stream through the Rust FFI and hands it to AudioPlayback.
- AudioPlayback creates one Android AudioTrack per remote member, feeds it PCM16 in blocking streaming mode and reports underrunCount. Its source comment says OS mixing is simpler and acceptable for a small call.
- AudioCapture owns AudioRecord with VOICE_COMMUNICATION, reads 10 ms frames and passes them to the FFI-published local track. Thus these paths do not use the bundled libwebrtc ADM for capture or render.
- DefaultCallAudioDeviceController selects one Android communication device (setCommunicationDevice on API 31+) and uses legacy SCO below/for Bluetooth routing. It demonstrates call routing, but does not demonstrate simultaneous built-in-mic capture and A2DP music output.

The correction matters: I retract the earlier inference that the native API’s automatic-playback wording meant ADM-owned playback. The implementation shows app-owned PCM capture and playback. The code says “one AudioTrack per remote member”; that choice alone is not evidence of a defect.

The most useful source is [AudioThread.kt](https://github.com/element-hq/element-call-android/blob/070830669d79bf76835f16321d3a4c1b102a2e98/call/impl/src/main/kotlin/io/element/android/call/impl/rtc/media/AudioThread.kt#L16-L50). Its maintainers report a Pixel 5 five-party measurement: 500 playback frames took 4.98–5.02 seconds with camera off and 5.45–5.97 seconds with camera on; about 15% of each track's output comprised underrun samples while RTP loss stayed at zero. Their diagnosed cause was blocking capture/playback loops sharing ordinary coroutine I/O workers with video and GC. They moved each loop to its own THREAD_PRIORITY_URGENT_AUDIO thread. Treat this as an in-source device observation, not an independent benchmark or proof that Volty has the same cause.

This native component is explicitly early: Element Call Android is 0.1.0-rc.7 and consumes matrix-rust-rtc 0.5.0-rc.2. That Rust/FFI layer embeds a LiveKit Rust client, but it is not a drop-in Java Room or JavaAudioDeviceModule replacement for Volty. The app-facing implementation and API are pre-release. Source files carry AGPL-3.0-only OR LicenseRef-Element-Commercial; do not copy into a closed-source app without resolving that license.

Pinned paths: [RustMatrixRtcMediaSession.kt](https://github.com/element-hq/element-call-android/blob/070830669d79bf76835f16321d3a4c1b102a2e98/call/impl/src/main/kotlin/io/element/android/call/impl/rtc/RustMatrixRtcMediaSession.kt#L499-L520), [AudioPlayback.kt](https://github.com/element-hq/element-call-android/blob/070830669d79bf76835f16321d3a4c1b102a2e98/call/impl/src/main/kotlin/io/element/android/call/impl/rtc/media/AudioPlayback.kt#L23-L27), [AudioCapture.kt](https://github.com/element-hq/element-call-android/blob/070830669d79bf76835f16321d3a4c1b102a2e98/call/impl/src/main/kotlin/io/element/android/call/impl/rtc/media/AudioCapture.kt#L32-L37), [DefaultCallAudioDeviceController.kt](https://github.com/element-hq/element-call-android/blob/070830669d79bf76835f16321d3a4c1b102a2e98/call/impl/src/main/kotlin/io/element/android/call/impl/audio/DefaultCallAudioDeviceController.kt#L119-L163).

### Signal Android / RingRTC: native ADM with optional Oboe, but a separate WebRTC ABI and call protocol

At Signal Android commit [92f5ccd3](https://github.com/signalapp/Signal-Android/commit/92f5ccd3a52c4780a0c916566e26280f640ba1de), ActiveCallManager owns call lifecycle and SignalAudioManager owns serialized route/focus/mode changes. On Android 12+, FullSignalAudioManagerApi31 enumerates availableCommunicationDevices and calls setCommunicationDevice. It also registers AudioRecordingCallback and logs whether an active recording exists, whether the client is silenced, the source and the input device. This is especially useful instrumentation for a call that appears connected without working capture. The route is one communication device; these sources do not establish built-in mic plus A2DP output.

At RingRTC commit [331d6018](https://github.com/signalapp/ringrtc/commit/331d601894f931337d24e9d56c68b94d28fc4555), CallManager.createPeerConnectionFactory() chooses either OboeAudioDeviceModule or JavaAudioDeviceModule and installs that ADM on its PeerConnectionFactory; the default AudioConfig.useOboe is false. With Oboe enabled, the config also controls software AEC/noise suppression, low-latency input and the voice-communication input preset. Remote WebRTC AudioTracks are enabled in the media callback and rendered/mixed by that shared WebRTC audio-device path, rather than by one Java AudioTrack allocated per remote member.

License and integration boundary: upstream Google Oboe is Apache-2.0, but that is only the native audio library. The RingRTC wrapper is AGPL-3.0-only; its Java API imports org.webrtc.audio.OboeAudioDeviceModule from Signal’s modified org.webrtc distribution and native/JNI build. This does not make the ADM a plug-compatible artifact for Volty’s LiveKit WebRTC runtime. The package classes, native symbols/ABI and build must match; the app also depends on RingRTC signaling/group-call protocol, so replacing LiveKit with RingRTC is a backend/protocol migration, not an audio-module swap. Reuse the configuration and recording-state diagnostics as reference; do not transplant the binding under the Oboe license.

Pinned paths: [CallManager.java](https://github.com/signalapp/ringrtc/blob/331d601894f931337d24e9d56c68b94d28fc4555/src/android/api/org/signal/ringrtc/CallManager.java#L264-L296), [AudioConfig.java](https://github.com/signalapp/ringrtc/blob/331d601894f931337d24e9d56c68b94d28fc4555/src/android/api/org/signal/ringrtc/AudioConfig.java#L10-L23), [AudioDeviceConfig.kt](https://github.com/signalapp/Signal-Android/blob/92f5ccd3a52c4780a0c916566e26280f640ba1de/app/src/main/java/org/thoughtcrime/securesms/webrtc/audio/AudioDeviceConfig.kt#L85-L95), [FullSignalAudioManagerApi31.kt](https://github.com/signalapp/Signal-Android/blob/92f5ccd3a52c4780a0c916566e26280f640ba1de/app/src/main/java/org/thoughtcrime/securesms/webrtc/audio/FullSignalAudioManagerApi31.kt#L73-L89), [SignalAudioManager.kt](https://github.com/signalapp/Signal-Android/blob/92f5ccd3a52c4780a0c916566e26280f640ba1de/app/src/main/java/org/thoughtcrime/securesms/webrtc/audio/SignalAudioManager.kt#L301-L355). Oboe’s license: [Google Oboe LICENSE](https://github.com/google/oboe/blob/master/LICENSE).

### Jitsi Meet: Java ADM render, with a mature Android routing controller

Jitsi Meet commit [36d4c1c7](https://github.com/jitsi/jitsi-meet/commit/36d4c1c7945016ecc588338ac0dff82cd060bbbf) pins react-native-webrtc 124.0.8. In that Android module, WebRTCModule creates a JavaAudioDeviceModule by default and attaches it to the PeerConnectionFactory; remote tracks remain WebRTC AudioTracks, so the app does not create a Java output track per participant. Jitsi’s AudioModeModule serializes route operations on a single executor, maps call volume keys to STREAM_VOICE_CALL, and delegates to a device handler. AudioDeviceHandlerGeneric sets MODE_IN_COMMUNICATION, speakerphone and Bluetooth SCO. This is a proven routing/control pattern, not a split built-in-mic/A2DP path. Jitsi sources are Apache-2.0; the pinned React Native WebRTC Android module is MIT.

## What is reusable for Volty

None of these inspected sources proves support for the exact desired split route: built-in phone microphone while call audio/music exits over Bluetooth A2DP, with normal duplex behavior when a headset is selected. Signal and Element select a communication device; Jitsi documents/implements speaker, earpiece, wired and Bluetooth call routing. Mark split routing as a separate device experiment, not an inherited capability.

The Element timing report makes per-member tracks a viable design option, not a known bad design. Its concrete pitfall is blocking writes on workers that do not get audio priority. Volty’s current AudioCapture.fill runs inside the injected Java ADM callback, likely already on WebRTC’s audio-record thread; PHONE sink.onData runs on an RTC callback. That differs from Element’s shared-IO coroutine loops, so do not move all audio to urgent threads on analogy alone.

Suggested isolated sequence:

1. Add diagnostics before changing audio: Android AudioRecordingCallback state/source/device/silenced, actual capture callback counts and thread/priority/duration, WebRTC audio/RTP stats, and per-remote AudioTrack.underrunCount plus write duration. This separates “no active mic capture” from capture pacing and remote output starvation, including the Xiaomi privacy-indicator symptom.
2. A/B the same 2- then 3-peer LiveKit room with PHONE custom per-remote sinks versus LiveKit/WebRTC’s normal remote-track rendering, holding capture, peer set and room fixed. This tests the custom renderer boundary without changing the LiveKit backend.
3. Only if the metrics show remote sink deadline misses, prototype a single isolated output change: enqueue one remote stream’s PCM frames to a bounded writer loop at urgent-audio priority, leaving ADM capture and all other tracks unchanged. Compare underruns, callback timing, RTP delivery and call survival before broadening it. The Element source supports this as a hypothesis to test, not as a prescription for Volty.

No code changes or device tests were made for this report.
