# Nearby: проект замены

Дата: 2026-10-03. Статус: проект для ревью пользователем; реализация не начата.

**Пересмотр после уточнения пользователя:** предложение сохранять UX групп
отозвано. Пользователь хочет модель Discord без текстового чата: приватные/
публичные серверы и голосовые каналы, а друзьям — прямые звонки. Новое продуктовое
направление записано в `2026-10-03-nearby-voice-spaces-design.md`. Технические
наблюдения этого документа сохраняются; разделы о прежнем UX и модели групп
являются историческим предложением, не утверждённой спецификацией новой системы.

## Задача и подтверждённые требования

Пользователь просит переписать Nearby с нуля. Полевые симптомы: участники не
видят или не слышат друг друга; один телефон показывает четырёх членов группы,
другой — двух; выбор микрофона телефона переключает воспроизведение на динамик.
Пользователь подтвердил нужный режим: микрофон телефона, голоса собеседников
в подключённых наушниках. LiveKit разрешено сохранить; вся логика Nearby подлежит
замене. Дополнительно сообщены двусторонняя тишина на Xiaomi и невозможность
нормально выйти из группы. Пользователь назвал телефон «xiaomi 17t pro», версию
системы — «latest», проявление — «всегда». Сохраняем название как сообщённое,
без подмены похожей моделью. Точный build Android/HyperOS фиксируется при сборе
диагностики. Xiaomi — обязательный отдельный сценарий приёмки.

Успех — согласованный состав группы, достоверное состояние голосовой связи,
восстановление после сетевых разрывов и проверенный маршрут звука. Количество
членов группы, людей в голосе и доступных точек на карте — разные величины,
каждая с явно названным смыслом. Отсутствие GPS не означает выход из группы.

## Что установлено чтением текущей реализации

Исследована чистая рабочая копия `main`, HEAD `7a80a7d6`. Вопреки исторической
записи AGENTS.md, локальная `feat/vehicle-composer` уже является предком HEAD;
Nearby и composer присутствуют в текущем коде. Старые ledgers социальных
планов прочитаны: это замена ранее реализованного функционала.

1. `AndroidLiveKitVoiceRoomEngine.applyMicrophoneSource()` для `PHONE`
   ставит `AudioDevice.Speakerphone` первым в `preferredDeviceList`.
   Настройка микрофона фактически меняет предпочтение аудиомаршрута. Это
   непосредственно объясняет сообщённое переключение на динамик.
2. `VoiceRoomEngine` публикует только список участников. Android-адаптер
   на любое событие Room обновляет этот список, но не передаёт наверх
   подключение, переподключение, отключение или ошибки треков.
   Репозиторий может оставаться `Joined` после потери реального соединения.
3. `LiveKitVoiceRoomRepository` не сериализует join/leave/mute и не ограждает
   поздние результаты идентификатором попытки. `activeGroupId` устанавливается
   только после connect: leave во время join не завершает эту попытку.
   Успешный старый join может затем восстановить уже отменённое состояние.
4. `NearbyScreen` считает членов из `RideGroup.members`, живых участников
   отображает из `SocialLiveEvent.Snapshot`, голосовых — из списка удалённых
   участников LiveKit. Последний список не включает локального пользователя.
5. Серверный `/groups/join` сохраняет membership и отвечает вошедшему,
   но не вызывает рассылку snapshot существующим подписчикам. Snapshot
   уже содержит всех членов через `group_members`, но изменение live snapshot
   само по себе не заменяет сохранённый `RideGroup.members` в клиенте.
6. Выход из группы/голоса блокируется общей `operation`, в том числе во время
   сетевого join/refresh. Локальный group cleanup запускается после ответа
   leave, а затем ожидает stop-sharing прежде отключения голоса. Backend
   разрешает выход владельца с передачей владения, но отклоняет выход последнего
   владельца. UI допускает этот выход. Эти механизмы могут объяснять отказ/
   задержку выхода; точный полевой сценарий ещё не воспроизведён.

Пункты 2–5 — подтверждённые дефекты/пробелы контрактов, а не доказательство
причины каждого случая отсутствия звука. Логи проблемных телефонов, фактическая
конфигурация работающего SFU и реальный медиатрафик ещё не исследованы.
Нельзя обещать исправление сетевого аудио только по этим наблюдениям.

## Варианты и рекомендация

1. **Рекомендуется: новое ядро Nearby, существующий LiveKit как транспорт.**
   Заменить владельцев состояния, синхронизацию, голосовой lifecycle,
   Android-аудиомаршрутизацию и соответствующие UI-контракты. Сохранить аккаунты,
   группы, друзей, приглашения и пользовательские данные. Даёт проверяемые
   границы и устраняет обнаруженные дефекты без самостоятельной разработки SFU.
2. Полная замена, включая голосовой SDK/SFU. Добавляет миграцию инфраструктуры,
   сетевые и аудиориски; свидетельств, что причиной является LiveKit, пока нет.
3. Локальные исправления существующих классов. Меньше изменений, но сохраняет
   раздельные модели состава и неполный контракт голосового движка; не отвечает
   запросу на замену подсистемы.

## Предлагаемая архитектура

### Выход — самостоятельная отменяемая операция

Различать выход из голосовой комнаты, прекращение текущей поездки/sharing и
выход из членства группы. Для каждого действия понятная кнопка и результат.
Выход из membership не блокируется другой операцией. Сразу отменяет местное
намерение быть в голосе/публиковать данные, отцепляет callbacks и останавливает
ресурсы независимо от ответа сервера. Backend-запрос имеет ограниченное ожидание;
offline/timeout отображается как неподтверждённый выход из membership, а не
ложный успех. При восстановлении сети идемпотентный запрос доводится до конца;
сбой не включает обратно микрофон/sharing. Повторный явный вход отменяет pending
leave только после разрешения его серверного результата.

Владелец с другими членами выходит с атомарной передачей владения (существующая
серверная политика). Если он последний, интерфейс прямо предлагает удаление
пустой группы с подтверждением. Это не скрытая ошибка после обычного «Выйти».
Все оставшиеся клиенты получают новый состав и владельца; бывший член теряет
backend- и SFU-доступ. Cleanup и повторы не затрагивают выбранную впоследствии
другую группу.

### Одна сессия группы

`NearbySession` владеет выбранной группой и единым неизменяемым состоянием.
Входящие события и команды обрабатываются последовательно. Состояние содержит
идентичность аккаунта/группы, состав, соединение с backend, sharing, координаты,
телеметрию и голосовую сессию. UI, карта и панели получают проекции из него.
Модуль BLE и навигация не становятся зависимостями голосового движка.

Каждая смена аккаунта/группы и отмена сессии меняет generation. Поздние ответы,
события старых подписок и permission callbacks не изменяют новую сессию.
Выход доступен во время подключения и восстановления; ожидание HTTP/SDK не
блокирует обработку отмены. Освобождение ресурсов завершает старую попытку,
даже если connect вернулся после команды leave.

### Серверный состав и синхронизация

Backend остаётся источником membership и разрешений. Новый контракт полного
snapshot содержит metadata группы, роли и всех её членов, optional координаты,
статус sharing, идентификатор поколения серверного потока и ревизию. Ревизия
упорядочивается при формировании snapshot, а не по клиентскому времени.
Membership меняется транзакционно; join/leave/delete/account deletion вызывают
обновление подписчиков. Повторная доставка безопасна.

После подключения/переподключения клиент получает полный актуальный snapshot;
старые ревизии текущего потока игнорирует. Snapshot и его доставка должны быть
согласованы так, чтобы не потерять изменение между initial snapshot и подпиской.
Внутри одного потока нет отката состояния при перестановке ответов. Новый
серверный поток требует полного snapshot, а не сравнения с прежней ревизией.

При сетевом разрыве последний состав сохраняется с отметкой «обновление
приостановлено». Нет свежих координат — нет новой точки. Отзыв sharing удаляет
доступ к координатам/телеметрии, но не членство. Отзыв членства очищает доступ
к группе и завершает голос; сервер также прекращает SFU-доступ удалённого
участника, а не полагается на добровольный disconnect клиента.

### Голос: состояние соединения и треков

Новый `VoiceEngine` передаёт типизированные события connection lifecycle,
участников, публикации локального микрофона, подписок на удалённые треки,
mute и ошибок. LiveKit-адаптер не принимает продуктовых решений.

Сессия различает `Idle`, `Connecting`, `Connected`, `Reconnecting`, `Leaving`,
`Failed`. Успех получения токена или появление человека в комнате не означает
доставку звука. UI отдельно показывает соединение, публикацию микрофона,
mute и доступность удалённых аудиотреков. Даже наличие трека не доказывает,
что человек физически слышит звук.

Единственный владелец Room, callbacks и аудиоресурсов. Повторный join не создаёт
вторую Room; смена группы прекращает старую. SDK-восстановление и приложение
не запускают конкурирующие reconnect. После окончательной потери сессии
приложение может получить свежий токен и повторить вход, пока сохраняется
явное намерение пользователя оставаться в голосе. Retry ограничен, с backoff;
отзыв доступа терминален. Намерение mute сохраняется при reconnect и применяется
до публикации нового трека. Logout прекращает голос независимо от backend.

### Независимые микрофон и выход

`AudioRouteController` управляет желаемым входом, желаемым выходом, списком
доступных устройств и фактически используемым маршрутом. Выбор микрофона
телефона не означает предпочтение Speakerphone. Требуемая комбинация — встроенный
микрофон и подключённые наушники. Смена/потеря гарнитуры публикуется как событие;
приложение показывает реальный fallback, не оставляет ложную подпись «наушники».

До выбора конкретного Android-адаптера необходимо проверить исходники именно
закреплённых LiveKit 2.25.3, WebRTC и локального AudioSwitch AAR. Раздельный
capture/render может потребовать собственного AudioRecord/WebRTC audio device
adapter. Готовый SDK-аудиосвитчер нельзя считать независимым выбором микрофона.
Нельзя одновременно отдавать управление маршрутом SDK и второму контроллеру.

Android `setPreferredDevice` задаёт предпочтение; принятие вызова не доказывает
фактический маршрут. Контроллер сверяет routed-device callbacks, а нужную
комбинацию проверяют реальным звуком. Если устройство не поддерживает сочетание,
UI сообщает это и предлагает доступный маршрут вместо молчаливого переключения.

Голос должен продолжаться при блокировке экрана и переходе в другие разделы
приложения: отдельный Android foreground-service lifecycle с уведомлением
mute/leave, разрешениями актуального targetSdk и корректным освобождением audio
focus. Process death не должен самовольно включать микрофон при новом запуске.

### UI и диагностика

Сохранить операции регистрации, друзей, групп и приглашений. Перевести экран
Nearby, карту группы и связанные панели на новую модель. Избавиться от старых
копий состава и голосового состояния после переключения всех потребителей.
UI явно различает «в группе», «в голосе», «на карте»; локальный участник учитывается
в голосовом счётчике. Соединение, mute и выбранные/фактические устройства видимы.
Строки в values и values-ru; решения вне Composable.

Диагностика связывает попытку подключения, server stream/revision, generation,
Room SID, publication/subscription и изменения маршрута. Экспорт для полевого
разбора не содержит токенов, паролей, аудиозаписей и точных координат. Детали
SDK доступны в диагностике, пользователь видит понятное состояние и действие.

## Проверка и критерии приёмки

- Четыре аккаунта в одной группе получают один состав после join/leave/reconnect;
  состав, список и счётчик на каждом клиенте построены из одной ревизии.
- Участник без GPS и sharing остаётся членом. Отзыв sharing убирает его данные,
  выход из группы убирает membership. Разрыв сети не превращается в пустую группу.
- Join → leave до возврата токена/connect не восстанавливает Room; join A → B
  игнорирует поздние события A. Logout и удаление группы прекращают голос.
- Повторные команды, перестановка snapshot, reconnect, отмена, ошибки publish/
  subscribe и mute при восстановлении покрыты детерминированными тестами.
  Fake engine сообщает lifecycle и треки, а не всегда успешное connect.
- Backend-контракт проверяется несколькими подписчиками с настоящей
  membership-мутацией, initial snapshot race и отзывом авторизации.
- На реальных телефонах: двусторонний звук при 2 и 4 участниках, разные сети,
  Wi-Fi ↔ мобильная сеть, краткий offline, блокировка экрана, возврат в приложение,
  отключение/подключение наушников, смена микрофона и mute во время reconnect.
- На наушниках пользователя: выбор PHONE действительно использует микрофон
  телефона и сохраняет воспроизведение в наушниках. Проверить wired/USB/BT
  отдельно на доступном оборудовании; не приписывать проверку отсутствующим
  устройствам. Зафиксировать модели телефонов, Android и гарнитур в отчёте.
- Xiaomi с сообщённой двусторонней тишиной: проверить отдельно без гарнитуры
  и с гарнитурой, audio focus, фактические capture/render devices, локальную
  публикацию, удалённую подписку и прохождение медиа. До успешной двусторонней
  проверки на этом телефоне этот дефект не объявлять устранённым.
- Выход обычного члена, владельца с другими членами и последнего владельца;
  выход во время join/refresh/reconnect, без сети, повторный выход и новый вход
  при позднем ответе. Локальный звук/публикация прекращаются независимо от
  успеха membership-запроса; результат подтверждён сервером либо явно pending.
- При невозможности маршрута/связи отображается фактическая проблема; статус
  «подключено» не продолжает утверждать работоспособность после disconnect.
- Полная Android suite перед каждым commit, backend suite отдельно, signed
  release APK; `git diff --check`. При изменении схемы — migration verification.
  Для mutation sweeps использовать только аудированный harness с новым nonce,
  очисткой результатов и точным количеством тестов. Compose/физический звук
  не объявлять проверенными по unit-тестам.

## Замена и совместимость

Замена внутренних контрактов целиком, а не добавление второго действующего
runtime поверх старого. Новое ядро проверяется изолированно и подключается одним
переключением DI, затем старые владельцы состояния удаляются. Аккаунты и друзья
сохраняются. Отзыв прежнего требования 2026-10-04: пользователь отменил перенос
старых групп; серверы создаются заново, исходные legacy-группы не удаляются.
Версионированный backend-контракт вводится совместимо
со старым клиентом; текущие REST/WS endpoints остаются до завершения перехода.
Эксплуатация нескольких backend-инстансов требует общей доставки/упорядочивания;
in-memory hub нельзя представлять как решение для нескольких процессов.

Этот документ не разрешает внешнее развёртывание. Сначала реализация, проверки
и конкретный результат для ревью, затем отдельный согласованный rollout.
