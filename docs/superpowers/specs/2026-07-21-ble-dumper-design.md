# BLE-дампер: инструмент для снятия сырого потока с колеса

Дата: 2026-07-21
Статус: дизайн утверждён

## Задача

Плану по Begode нужны реальные байты. Спека
`2026-07-21-multi-pack-bms-design.md` реконструировала формат кадров по
исходникам WheelLog и разбору железа T4, но три вещи остаются гипотезами:

1. какие типы кадров колесо шлёт на самом деле;
2. какие значения принимает `bmsnum` в кадре `0x01` — предполагается 0..3 как
   (ветка × сборка);
3. сколько ячеек приходится на ветку — 24 у T4 против 40 у ET Max.

Нужен инструмент, который снимет сырой поток с FFE1 за первые 10–15 секунд
после подключения и отдаст файл. Владелец колеса — не разработчик в момент
съёма: он стоит рядом с колесом с телефоном в руке, и ему должно быть видно,
что дамп получился, до того как он уйдёт.

## Решение

Отдельное Android-приложение `:dumper` в репозитории volty. Свой
`applicationId`, свой APK, ноль зависимостей от кода volty — общий только
каталог версий и `./gradlew`. Ставится рядом с volty и не мешает ему.

Модуль устроен как KMP с единственным `androidTarget`, повторяя форму
`:composeApp`. Это не про кроссплатформенность: так переиспользуются плагины,
уже объявленные в каталоге (`kotlin-multiplatform`, `android-application`,
`compose-multiplatform`, `compose-compiler`), и в `libs.versions.toml` не
приходится добавлять `kotlin-android` ради одного модуля.

Разрешения в манифесте — те же, что у volty, и по той же причине:
`BLUETOOTH_SCAN` (с `neverForLocation`) и `BLUETOOTH_CONNECT` для API 31+, плюс
устаревшие `BLUETOOTH`, `BLUETOOTH_ADMIN` и `ACCESS_FINE_LOCATION` с
`maxSdkVersion="30"` — без последнего BLE-скан на API 26–30 молча не находит
ничего.

`FileProvider` с авторитетом `${applicationId}.fileprovider` и
`<cache-path name="dumps" path="dumps/" />`.

## Компоненты

Пять файлов, каждый с одной ответственностью.

| Файл | Ответственность | Зависит от |
|---|---|---|
| `MainActivity.kt` | запрос разрешений, хост Compose | Android, Compose |
| `DumperScreen.kt` | UI: список устройств → подключение → счётчики → «Стоп и отправить» | `DumpRecorder`, `FrameSanity` |
| `DumpRecorder.kt` | Kable: скан, подключение, подписка на FFE1, выдача байтов наружу | Kable |
| `FrameSanity.kt` | **чистая логика**: кормится байтами, считает кадры и наблюдения | ничего |
| `DumpWriter.kt` | копит строки, пишет файл в кэш, отдаёт в «Поделиться» | Android |

`FrameSanity` не знает про BLE, не знает про файлы и ничего не расшифровывает —
он только синхронизируется по потоку и считает. Поэтому он единственный, кто
покрывается тестами, и покрывается полностью.

`DumpRecorder` не решает, что делать с байтами: он отдаёт их наружу колбэком,
как `ConnectionSession` в volty после Task 4. Экран раздаёт их в `FrameSanity`
и `DumpWriter`.

## UUID и подключение

Сервис `0000ffe0-0000-1000-8000-00805f9b34fb`, характеристика
`0000ffe1-0000-1000-8000-00805f9b34fb` — та же на чтение и запись.

**Дампер ничего не пишет в характеристику.** Колесо стримит само, хендшейк ему
не нужен, а FFE1 у Begode — командный канал: туда уходят управляющие символы
(свет, режим педалей, тилтбэк). Слать в него что-либо, не зная протокола
наверняка, значит рисковать перенастроить колесо под человеком. Дампер
исключительно слушает.

Скан показывает **все** устройства с их именем, адресом и RSSI, без фильтра по
UUID: имя модуля Begode заранее неизвестно, а FFE0 в рекламном пакете
объявляется не всегда.

## Формат файла

Файл — главный артефакт, поэтому он самодостаточен и читается глазами.

```
# volty-dumper 1.0
# device: GotWay_1234 (AA:BB:CC:DD:EE:FF)
# service 0000ffe0 / char 0000ffe1
# started 2026-07-21T15:04:05Z
# columns: t_ms hex
0     4e414d453a...
118   55aa0000c4...
236   55aa01...
...
# --- summary ---
# notifications 412  bytes 8240  frames 340
# frame types seen: 00 01 02 03 04
# bmsnum values (type 01): 0 1 2 3
# max cell packet index (types 02/03): 4
```

Время — миллисекунды от начала записи, не абсолютные: для разбора протокола
важны интервалы между кадрами, а дата только шумит.

Пишется **весь поток в hex, без фильтрации**, включая ASCII-строки `NAME:`,
`GW…`, `MPU…`, которые колесо шлёт в начале сессии. Они восстанавливаются из тех
же байтов, и отдельная обработка им не нужна.

Одна строка на нотификацию, а не на кадр: кадр в 24 байта при MTU 23 приезжает
разрезанным, и как именно он разрезан — само по себе полезное наблюдение для
парсера.

## Счётчики на экране

Три счётчика отвечают ровно на три вопроса из «Задачи», поэтому ответ виден на
телефоне сразу, не дожидаясь разбора файла:

- **типы кадров** — множество значений `buff[18]` у собранных кадров;
- **значения `bmsnum`** — множество `buff[19]` у кадров типа `0x01`; если там
  окажется `0 1 2 3`, гипотеза «ветка × сборка» подтверждена, если `0 1` —
  опровергнута;
- **максимальный номер пачки ячеек** — наибольший `buff[19]` у кадров `0x02` и
  `0x03`; отсюда число ячеек на ветку (пачка = 8 ячеек).

Плюс счётчики нотификаций, байтов и собранных кадров — чтобы отличить «идёт
запись» от «подключились, но тишина».

Это **не расшифровка значений**: читаются два байта по известным смещениям, а
напряжения, токи и температуры не трогаются вообще. Расшифровка — работа
`BegodeProtocol`, и писать её дважды, второй раз по тем же догадкам, которые
дамп и должен проверить, бессмысленно.

## Синхронизация кадров

`FrameSanity` копит входящие байты и ищет заголовок `55 AA`; кадр — 24 байта;
хвост `5A 5A 5A 5A` проверяется. При несовпадении хвоста буфер сдвигается на
байт вперёд и поиск продолжается — мусор в потоке не должен ломать счётчики
навсегда.

## Отказы

| Ситуация | Поведение |
|---|---|
| разрешения не выданы | экран объясняет, зачем, и просит |
| Bluetooth выключен | сообщение, кнопка повторить |
| устройство не найдено / отвалилось | состояние показано; **записанное не теряется**, отправить по-прежнему можно |
| подключились, но нотификаций нет | счётчики стоят на нуле — это и есть диагноз |

Запись останавливается вручную или сама через 60 секунд: для разбора протокола
этого с запасом, а файл не разрастается.

## Тесты

`FrameSanityTest` — векторы байтов:

- корректный кадр `55 AA` + 24 байта + хвост → тип и `bmsnum` учтены;
- кадр, **разрезанный между чанками** — при MTU 23 это норма, а не редкий
  случай;
- мусор перед заголовком → ресинхронизация, кадр всё равно собран;
- битый хвост → кадр не засчитан, следующий корректный засчитан;
- накопление множеств: типы и `bmsnum` не дублируются и не теряются.

BLE-часть юнит-тестами не покрывается — как и в volty.
