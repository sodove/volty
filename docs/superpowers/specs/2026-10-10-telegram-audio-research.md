# Telegram Android audio and group voice: source review

Source snapshot: [`DrKLO/Telegram` commit `f2908b14133bbffbf7ab04f641ecb5bfaf533242`](https://github.com/DrKLO/Telegram/tree/f2908b14133bbffbf7ab04f641ecb5bfaf533242), checked 2026-10-10. This is a source-path review, not a diagnosis of Volty’s reported device symptoms and not a claim that Telegram was tested on the same hardware.

## Call paths

Private calls and group calls share the Java `VoIPService`, but enter different native constructors. Private calls go through `Instance.makeInstance` → `NativeInstance.make` → JNI `makeNativeInstance` → the version-selected `tgcalls::Meta::Create` implementation; the current `InstanceImpl` hands work to `Manager` and `MediaManager`. The `MediaManager` creates a platform-default WebRTC `AudioDeviceModule` (ADM), creates a WebRTC voice engine and `AudioState`, then attaches its send and receive channels. The selected implementation is versioned, so this describes the current tgcalls path, not every historical negotiated version. [VoIPService private-call setup](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/VoIPService.java#L3410-L3477) · [JNI private-call construction](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/org_telegram_messenger_voip_Instance.cpp#L828-L995) · [`InstanceImpl`](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/InstanceImpl.cpp#L28-L40) · [`MediaManager`](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/MediaManager.cpp#L307-L446).

Group voice goes through `NativeInstance.makeGroup` and the JNI bridge constructs `GroupInstanceCustomImpl`. In RTC mode, that implementation creates one ADM and one WebRTC voice engine / `Call`; it then creates an `IncomingAudioChannel` per remote SSRC/participant. Each incoming channel gets a WebRTC `VoiceChannel` attached to that same call and transport. Its audio options enable jitter-buffer fast acceleration and set a 50 ms minimum delay. [Java group constructor](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/NativeInstance.java#L70-L81) · [JNI group constructor](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/org_telegram_messenger_voip_Instance.cpp#L491-L632) · [group ADM, `Call`, and shared `AudioState`](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/group/GroupInstanceCustomImpl.cpp#L1523-L1600) · [per-SSRC receive channels and jitter options](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/group/GroupInstanceCustomImpl.cpp#L800-L907).

## Group render, mixing, and volume

The Android group RTC path is **per-participant receive channels feeding WebRTC’s shared mixer and one ADM playout callback**. Telegram does not allocate one device `AudioTrack` per remote participant in this path. `WebRtcVoiceEngine::Init` creates or accepts one `AudioMixerImpl`, builds one `AudioState` around that mixer and ADM, and registers the `AudioState` transport as the ADM callback. Group channels share the `AudioState` from the same `VoiceEngine`; WebRTC therefore renders the mixed receive audio through the single ADM output path. `IncomingAudioChannel` also installs a raw decoded-audio sink for level/frame observation; that sink is not its device output. [WebRTC voice-engine setup](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/webrtc/media/engine/webrtc_voice_engine.cc#L374-L425) · [group channels share `Call` / audio state](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/group/GroupInstanceCustomImpl.cpp#L1577-L1594).

Telegram has a separate participant-volume control. Java calls `NativeInstance.setVolume(ssrc, volume)`; the group implementation finds that participant’s receive channel and calls `SetOutputVolume`, which sets gain on the matching WebRTC receive stream. This is distinct from the system’s call-volume stream and from capture AGC. [group volume API and dispatch](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/NativeInstance.java#L218-L221) · [SSRC volume application](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/group/GroupInstanceCustomImpl.cpp#L3478-L3499) · [receive-stream gain](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/webrtc/media/engine/webrtc_voice_engine.cc#L2354-L2369).

The shared WebRTC engine has echo cancellation and automatic gain control enabled in its default voice options; it can use supported platform AEC/NS effects, with WebRTC processing configured as appropriate. Private-call config separately checks Android AEC/NS availability and Telegram server settings before choosing system versus WebRTC processing. Do not treat those flags as a promise that every device or group-call mode runs the same processing chain. [voice-engine processing options](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/webrtc/media/engine/webrtc_voice_engine.cc#L427-L438) · [private-call effect selection](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/VoIPService.java#L3396-L3420).

## Android device policy and Bluetooth

For its self-managed call path, `VoIPService.configureDeviceForCall` sets normal calls to `USAGE_VOICE_COMMUNICATION` / `STREAM_VOICE_CALL`, selects `MODE_IN_COMMUNICATION`, requests transient audio focus for `STREAM_VOICE_CALL`, and applies speaker/earpiece/Bluetooth routing. If Android Telecom `ConnectionService` is active, Telegram delegates route selection to its `CallAudioState`; otherwise its Bluetooth route starts SCO and waits for the SCO state callback before switching. The route choices in this code are speaker, earpiece/wired, and Bluetooth communication—not an independent input selector plus an A2DP music-output selector. [route setup](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/VoIPService.java#L3833-L3889) · [self-managed voice mode, focus, usage, and SCO route](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/VoIPService.java#L4813-L4887).

**Conclusion on phone mic + classic Bluetooth A2DP output:** Telegram’s inspected code does not establish that feature. Its call route uses Bluetooth SCO (the headset communication/HFP path) or Telecom’s generic Bluetooth call endpoint; it does not select `TYPE_BLUETOOTH_A2DP` for call playback or show a phone-mic/A2DP split. Android documents A2DP as high-quality Bluetooth streaming and SCO as the telephony headset route; current `setCommunicationDevice()` selects a communication sink and lets the platform select its matching source. Thus Telegram is evidence for mature voice routing and full-duplex headset routing, not evidence for preserving music over A2DP while the phone mic captures. Concurrent music behavior is also not established by these call-route methods. [Android Bluetooth profiles](https://developer.android.com/develop/connectivity/bluetooth/profiles) · [`AudioManager` communication-device API](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo)) · [Telegram Bluetooth route code](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/telegram/messenger/voip/VoIPService.java#L3833-L3889).

The platform-default ADM is the important reusable boundary: direct and group RTC paths let WebRTC own capture/playback and the shared render path, while Java handles focus and route policy. WebRTC’s Java ADM builder can set the audio source and the track attributes; the module exposes a runtime preferred-input-device method. Its default Java input source is `VOICE_COMMUNICATION`; that backend has dedicated urgent-priority capture and playback threads. Telegram’s native code requests a platform-default ADM rather than proving that every Android device takes the Java ADM backend, so these Java details describe an available WebRTC customization seam, not a guaranteed Telegram runtime backend. The native group path also separates WebRTC media/network/worker roles and uses blocking calls to marshal channel setup to the worker and network threads. [WebRTC Java audio-source builder](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/JavaAudioDeviceModule.java#L37-L104) · [track attributes](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/JavaAudioDeviceModule.java#L205-L214) · [preferred input device](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/JavaAudioDeviceModule.java#L428-L437) · [default Java audio source](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/WebRtcAudioRecord.java#L57-L66) · [Java capture loop](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/WebRtcAudioRecord.java#L112-L156) · [Java playout loop](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/src/main/java/org/webrtc/audio/WebRtcAudioTrack.java#L92-L178) · [group thread marshalling](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/group/GroupInstanceCustomImpl.cpp#L822-L833) · [platform-default ADM request](https://github.com/DrKLO/Telegram/blob/f2908b14133bbffbf7ab04f641ecb5bfaf533242/TMessagesProj/jni/voip/tgcalls/MediaManager.cpp#L428-L446).

## Transferable patterns for Volty

1. **Keep one SDK-owned ADM for one call.** Let WebRTC own capture timing, buffering, playout, and the multi-peer mix. Use route policy around that shared device module. This is the clearest structural alternative to disabling SDK recording and driving a second `AudioRecord` loop.
2. **Keep per-peer gain in the receive graph.** Set a remote participant’s gain on its WebRTC receive stream; leave Android’s call/media volume to the system. This avoids one output track, lock, and queue per remote for ordinary group voice.
3. **Keep the existing injection seam, and decide what the injected ADM owns.** Volty already supplies its owned module through `LiveKitOverrides(AudioOptions(audioDeviceModule = ...))` in [`AndroidVoiceSdkSession.allocateRoom`](../../../composeApp/src/androidMain/kotlin/ru/sodovaya/volty/data/voice/AndroidVoiceSdkSession.kt#L119). Telegram reinforces the architectural boundary—one ADM owns call capture and shared playout—but its `tgcalls` module is not a drop-in LiveKit ADM implementation or ABI. The useful design question is whether Volty’s currently injected module should retain SDK capture and shared render; the current custom `AudioRecord` callback loop is a different ownership choice. This source review does not establish that a phone-mic/A2DP split can be achieved inside the ADM.

Telegram’s signalling, encryption, and `tgcalls` channel implementation cannot be transplanted as a render-only component into LiveKit. The transplantable ideas are ADM ownership, shared WebRTC mixing, jitter settings per receive channel, and per-stream gain. Choosing the phone mic while sending call render to A2DP remains a separate Android routing experiment and needs device-level validation.

## Source/license note

The inspected Telegram Android VoIP Java files carry GPL-2.0-or-later headers; the separate official [`TelegramMessenger/tgcalls`](https://github.com/TelegramMessenger/tgcalls) repository identifies its library as LGPL-3.0; the included WebRTC Android audio files have BSD-style headers.
